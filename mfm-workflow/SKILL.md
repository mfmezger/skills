## When to Use
Invoke at the START of essentially any coding task in Marc's projects — 'follow mfm-workflow', 'let's build X', or just when a coding task begins. It defines HOW we work together across nine steps: Investigate → Plan → Grill → Loop → Review → Commit → Push → Open PR → Debug pipeline, plus a Measure step for model, prompt or data changes and a short close-out. It is ADAPTIVE: run the full flow for a feature; collapse the early steps for a small fix, but NEVER skip Review, Commit, and the PR. It is the orchestration layer — each step delegates to a focused skill; this skill's job is to run them in order, scale them to the change, and keep the user in the loop at the decision points.

## Procedure
1. SIZE THE CHANGE FIRST. Trivial (typo, one-liner, obvious fix in known code) → collapse to Loop → Review → Commit → Push → PR. Feature or anything touching unfamiliar code / contracts / data / auth → run all nine steps. State which mode you have chosen and why, in one line, before starting.
2. STEP 1 — Investigate problem. Use the `understand-codebase` skill: dispatch a scout subagent to map the area, and IMMEDIATELY keep talking to the user about the feature while it runs. Do not block. For a whole-system question, use graphify instead. Skip only for a trivial change in code you already know.
3. STEP 2 — Formulate plan. Use the `capy` skill (company standards / conventions / approved-way questions) to ground the plan in house rules BEFORE inferring conventions from local code. Produce a concrete plan: what changes, which files (from the scout's extension-point map), what the tests will assert, and the rollback/PR granularity (one PR or a stack). Name the core data shape and where external data is parsed before any logic (`engineering-principles`: domain model, boundaries and types; for retries, CronJobs or migrations also idempotency and migrations). Classify every artifact the task produces: what may be committed (code, IDs, labels, paraphrases) and what must stay local (anything with real customer or product data, e.g. analysis reports). For model, prompt or data changes, the plan also names the baseline, the metric and the estimated cost of the measurement (step 4b).
4. STEP 3 — Grill me. Use the `grill-me` / `grilling` skill: resolve the plan's open decisions in dependency order, ALWAYS offering your recommended answer. Ask dependent decisions one at a time; batch independent ones into one structured question set (e.g. `ask_user_question`, recommended option first). Answer from the codebase whatever the codebase can answer instead of asking. Before adopting a convention you found in data (golden sets, logs, legacy behaviour), check it against the repo's normative sources (prompts, rules, regulation they cite) and surface any conflict as its own decision. Do not proceed to Loop until the plan is shared and the unknowns are closed.
5. STEP 4 — Loop. Implement in the discover → change → verify cycle. Write or run a failing test first where it makes sense (red-before-green), reuse the abstractions the scout found rather than reinventing them, and keep the gate (type-check / lint / tests) green as you go. This is the one step with no sub-skill — it is just disciplined implementation, guided by `engineering-principles` (root causes when debugging: after two failed fixes on one premise, write the premise down and test it before a third; verification before calling anything done). Use subagents for implementation unless it is a single small feature; as soon as there are two or more features that are not directly linked, implement them with subagents. Give every worker a self-contained brief: the decisions already made, the exact files and extension points, what it must NOT do (commit, push, live/paid calls, touching real data or other worktrees), the data-handling rule, and the gate commands with the versions CI uses. When a worker fails or stops, inspect `git status` / `git diff` and run the gate before anything else: it often left most of the work done; finish small remainders inline instead of re-dispatching blindly.
6. STEP 4b — Measure (model, prompt or data changes only). Measure the effect against the baseline fixed in the plan, with the same metric, judge and settings as the baseline. Reuse existing results first (earlier runs often already cover a split); paid live runs are a decision point: state the estimated cost and get the user's OK. Separate effects where it is cheap (e.g. rescore old predictions against corrected labels before paying for a fresh run). Report before/after, run-to-run spread and what the dataset cannot show. Vet every number with the `benchmark-checklist` skill before reporting or acting on it.
7. STEP 5 — Review. Run the `interrogate` skill: two FRESH reviewer subagents on different model families (default litellm/claude-opus-5-5 + litellm/gemini-3-8-flash), same brief, no implementation context, judged against `thermo-nuclear-code-quality-review` and `blast-radius`. Each reproduces the bug/fix itself, proves the tests are non-vacuous (mutation checks in a throwaway /tmp copy, never in the worktree), checks the data-handling rule on every committed artifact, and runs the gate. You are the lead reviewer: merge findings, weight cross-family agreement, sort them into Act on / Consider / Noted / Dismissed, and return GO (Act on empty) or REWORK. On REWORK, loop back to step 4 with the Act on list, then run a NEW panel that gets the old list and verifies each item is done, not just present. Do NOT self-approve non-trivial work. For a genuinely trivial change, an inline self-review against the standard is acceptable.
8. STEP 6 — Commit. Use the `commit` skill: Conventional Commits, required type+scope, imperative <=72-char subject, body only if it earns its place. One focused commit per logical change.
9. STEP 7 — Push. Push the branch (git push -u origin <branch>). Never --force; use --force-with-lease if a rebase requires it.
10. STEP 8 — Open PR. Use the `ado-pr-generate` skill against Azure DevOps (pass the org explicitly — confirm it from the git remote; verify the PAT by probing for a 200, not by trusting the env var name). Active not draft unless asked. Put long evidence in a PR comment (ADO caps descriptions at 4000 chars). The description states the measured effect (step 4b), the production cost/latency impact, and side effects reviewers would otherwise trip over (e.g. changed dataset digests, re-recorded fixtures).
11. STEP 9 — Debug pipeline. After the PR opens CI, use the `ado-pipeline-analysis` skill to check the build and read failing-step logs. Reproduce failures locally (the gate must pass on the real post-merge state — the PR merged into the current target branch — not just the branch) and push fixes until green.
12. Keep the user at the decision points: which plan (step 2/3), GO/REWORK outcomes (step 5), paid live runs (step 4b), pushing or deleting tags, anything that triggers a deploy, and the merge are theirs to confirm. Merge only after step 9 is green, and only when the user explicitly says so. Do the mechanical steps autonomously; surface the judgement calls.
13. Close out. Give the user the result in one place (PR link, measured effect, open questions); put reports with real data in a local file outside the repo. Save durable lessons (tool quirks, project conventions) to memory or propose them as changes to this skill.

## Pitfalls
- Do not skip straight to coding. The most expensive mistakes in this workflow happen because Investigate (step 1) and Grill (step 3) were skipped — you reinvent an existing abstraction, or you build the wrong thing well.
- Do not commit on main unless explicitly asked. Normally work on a branch in a separate worktree.
- Adaptive is not an excuse to drop Review/Commit/PR. Ceremony scales DOWN for small changes but those three are the floor — a 'trivial' change that skips review is how silent regressions ship.
- Do not self-approve non-trivial work in step 5. A fresh reviewer with no implementation context catches things the author literally cannot see (a fix whose own test asserts against the wrong config; a fix that creates the next instance of the bug it fixed). Run the interrogate panel; a second model family catches what the first one systematically misses.
- Do not block waiting for the step-1 scout. Dispatch it and keep grilling the user about the feature — the two run in parallel by design.
- Always recommend an answer when grilling. Batching DEPENDENT questions is bewildering, and asking what the codebase already answers wastes the user's attention; batching INDEPENDENT ones in a structured set saves round-trips.
- Do not adopt a convention from data just because it is consistent. A golden set can be consistently wrong against the rules the product must follow; implementing it teaches the model the mistake.
- capy (step 2) is the FIRST stop for 'what's our standard / approved way' — consult it BEFORE inferring conventions from local code, or you will encode drift as if it were policy.
- The gate passing on your branch is not proof; step 9 requires the gate green on the real post-merge state. Bases move under branches (a merged sibling PR can break yours with zero textual conflict).
- Several referenced skills are installed via symlink and can go dangling (grilling, code-review, diagnosing-bugs have all been seen empty). If a step's skill resolves to nothing, check `readlink -f` and restore it before assuming the step is optional.
- Do not resume a completed subagent session (scout or reviewer) — it exits with no output. Spawn a fresh one with the context pasted in.
- Run the gate with the tool versions CI / pre-commit pin (e.g. `uvx ruff@<pin>`, `uv run --with ty==<pin>`) when the project venv lacks them. `pre-commit run --all-files` skips untracked files: run it with `--files` on new files before committing.
- A change that alters the sequence of external calls (an extra LLM request, a retry) breaks recorded fixtures such as VCR cassettes: re-record only the affected ones and check them for secrets.
- Model-facing text (prompts, retry messages) belongs where the project keeps its other prompts, versioned and part of any prompt digest, not as a constant in code.
- In a fresh worktree, gitignored runtime assets (`.env`, local datasets) are missing; symlink them in. `ln -s <target> <existing-dir>` creates the link INSIDE that directory: link the children or remove the directory first.

## Verification
1. Mode was declared up front (full flow vs collapsed) and matched the size of the change.
2. For non-trivial work: a scout ran in step 1, a plan was grounded in house rules (capy) and shared via grilling before any code, and an interrogate panel (two model families, lead judgment) returned GO before commit (a new panel after every REWORK).
3. For model, prompt or data changes: the effect was measured against the planned baseline, paid runs were approved, and the numbers are in the PR. No committed artifact contains data classified as local-only.
4. Every change is behind a Conventional Commit and an Azure DevOps PR — no direct-to-main work unless the user explicitly asked for it.
5. The gate is green on the real post-merge state, not just the branch, and any pipeline failure was read via ado-pipeline-analysis and fixed.
6. The user confirmed the plan, the GO/REWORK outcome, and the merge — the judgement calls were surfaced, the mechanical steps were done autonomously.
